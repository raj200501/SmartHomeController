# Architecture Overview

This document describes the Smart Home Controller CLI simulator architecture, the flow of data through the system, and the major Objective-C modules used to implement the behavior described in the README.

## Goals

1. **Deterministic execution** so repeated runs produce predictable output.
2. **Small and composable modules** that map directly to smart home concepts.
3. **Clear separation between configuration, runtime state, and commands.**
4. **Easy to verify** via unit tests and smoke tests.

## High-Level Components

The CLI application is composed of the following layers:

- **CLI Parsing:** Converts user input into strongly typed commands.
- **Configuration Loading:** Reads device and scene definitions from plain-text files.
- **Device Model:** In-memory representation of lights, thermostats, and cameras.
- **Controller:** Applies actions to device models and persists state.
- **State Store:** Saves and loads device status from disk.
- **Scene System:** Batch-applies multiple device actions.
- **Output Formatting:** Produces human-readable status and JSON output.

## Module Map

| Module | Responsibility |
| --- | --- |
| `SHCCommandParser` | Parse CLI args into `SHCCommand` objects. |
| `SHCController` | Apply device mutations and provide status listings. |
| `SHCConfig` | Load devices from `config/devices.conf`. |
| `SHCSceneConfig` | Load scenes from `config/scenes.conf`. |
| `SHCSceneRunner` | Execute scene actions on devices. |
| `SHCStore` | Read/write `data/state.db`. |
| `SHCJson` | Render device state in JSON format. |
| `SHCStringBuilder` | Assemble multiline output efficiently. |

## Data Flow

The CLI flow for a typical invocation is:

1. **Startup**
   - Environment variables are read for config paths and log level.
   - A `SHCCommand` is created by the command parser.

2. **Device Loading**
   - `SHCConfig` reads `devices.conf` and constructs device models.
   - `SHCStore` attempts to load the last-known state.

3. **Command Execution**
   - For device commands, `SHCController` applies the requested change.
   - For scene commands, `SHCSceneRunner` applies multiple device changes.

4. **Persistence**
   - If a state file is configured, the current device state is saved.

5. **Output**
   - Status, dashboard, or scene output is printed to stdout.

## Device Model

Every device is represented by a base `SHCDevice` struct. Specialized devices embed the base struct:

```
SHCDevice
  ├─ SHCLight
  ├─ SHCThermostat
  └─ SHCCamera
```

### Common Fields

- `identifier`: stable, unique ID
- `name`: human-readable label
- `location`: physical location in the home
- `type`: enum indicating light/thermostat/camera
- `isOnline`: simple connectivity flag

### Light

Lights include:

- `isOn`: on/off state
- `brightness`: 0-100 (clamped)

### Thermostat

Thermostats include:

- `currentTemperature`: current sensed value
- `targetTemperature`: desired target
- `units`: `C` or `F`
- `minTemperature` / `maxTemperature`: clamp boundaries

### Camera

Cameras include:

- `isStreaming`: streaming on/off
- `lastSnapshotId`: incremented when snapshots are taken

## Configuration Parsing

### Devices

`SHCConfig` parses each non-empty, non-comment line in `devices.conf`:

1. `type`
2. `identifier`
3. `name`
4. `location`
5. optional `attributes` (comma-separated `key=value` pairs)

Attributes are interpreted based on device type:

- **light**: `brightness`
- **thermostat**: `current`, `target`, `units`
- **camera**: `streaming`

### Scenes

Scene parsing is line-oriented. A scene starts with:

```
scene,<name>,<summary>
```

Subsequent lines define device actions until `end` is reached.

Supported actions:

- `light,<id>,power=on|off`
- `light,<id>,brightness=<0-100>`
- `thermostat,<id>,target=<temp>`
- `camera,<id>,streaming=on|off`

Each action becomes a `SHCSceneAction`, stored in the scene’s `actions` array.

## State Store

The state file is a plain-text log of device values. Example:

```
light-living power=on brightness=60
thermo-main current=21.5 target=22.0 units=C
cam-front streaming=on last_snapshot=3
```

This file is generated by `SHCStore` and re-applied during startup. The state file does **not** override the device inventory—it only adjusts runtime fields (like brightness or target temperature) for devices that already exist in `devices.conf`.

## Output Formats

### Status (Human-Readable)

```
Living Room Lamp (light-living) in Living Room [online=yes] | power=on brightness=75%
```

### Status (JSON)

```
{"devices":[{"id":"light-living","name":"Living Room Lamp",...}]}
```

### Dashboard

The dashboard aggregates device states to provide a quick system summary:

- Number of lights on
- Number of cameras streaming
- Average thermostat temperature

## Error Handling Strategy

The CLI intentionally favors direct, deterministic error handling:

- Invalid config lines are logged and skipped.
- Unknown device IDs cause command failures with explicit messages.
- Memory allocation failures exit immediately with an error message.

This ensures verification scripts can rely on predictable exit codes and outputs.

## Testing Strategy

Testing is split into:

1. **Unit tests** for string utilities, configuration parsing, and device state.
2. **Scene tests** to validate parsing and application of actions.
3. **State store tests** to ensure persistence works correctly.
4. **Smoke tests** in `scripts/verify.sh` to validate end-to-end behavior.

## Extensibility Notes

Adding new device types requires:

1. A new `SHCDeviceType` entry.
2. A new struct embedding `SHCDevice`.
3. Parser support in `SHCConfig`.
4. Controller support in `SHCController`.
5. State store read/write logic in `SHCStore`.

Adding new scene actions requires:

1. A new `SHCSceneActionType` entry.
2. Parser support in `SHCSceneConfig`.
3. Execution support in `SHCSceneRunner`.

## Design Principles

- **Simple text configuration** for transparency and versioning.
- **Single source of truth** for device inventory (device config).
- **Minimal dependencies** to ease CI and reproducibility.
- **Small, focused functions** for easy unit testing.

## Example Lifecycle

1. Define a device inventory in `config/devices.conf`.
2. Define a scene in `config/scenes.conf`.
3. Run `./scripts/run.sh dashboard` to view the aggregated state.
4. Run `./scripts/run.sh scene run evening` to apply a scene.
5. Inspect `data/state.db` to see saved state.
